\hypertarget{introducciuxf3n}{%
\section{INTRODUCCIÓN}\label{introducciuxf3n}}

En la actualidad, la seguridad perimetral constituye uno de los pilares
fundamentales para la protección de la información dentro de cualquier
organización. El crecimiento constante de los servicios conectados a
Internet, sumado al incremento de amenazas como accesos no autorizados,
escaneo de puertos, ataques de fuerza bruta y explotación de
vulnerabilidades en servicios expuestos, obliga a las instituciones a
implementar mecanismos de control de tráfico capaces de segmentar sus
redes y filtrar las comunicaciones entre zonas de distinta confianza.

Dentro de este contexto, los cortafuegos (firewalls) de nueva generación
basados en software libre, como \textbf{OPNsense}, se han convertido en
una alternativa robusta, flexible y de bajo costo para pequeñas y
medianas organizaciones, así como para entornos académicos de
simulación. OPNsense es una distribución de firewall y enrutador de
código abierto, basada en FreeBSD, que ofrece una interfaz web intuitiva
y un conjunto amplio de funcionalidades empresariales: filtrado de
paquetes con estado (\emph{stateful firewall}), traducción de
direcciones de red (NAT), redes privadas virtuales (VPN), portal
cautivo, sistema de detección/prevención de intrusos, balanceo de carga,
alta disponibilidad, entre otras.

La presente práctica (PAE 5) tiene como propósito que el estudiante
construya, dentro de un entorno completamente virtualizado mediante
\textbf{GNS3} (integrado con máquinas virtuales QEMU/VMware), una
infraestructura de red segmentada en tres zonas de seguridad
---\textbf{WAN}, \textbf{LAN} y \textbf{DMZ}--- gestionadas por un
equipo OPNsense que actúa simultáneamente como enrutador y cortafuegos
perimetral. Sobre esta infraestructura se aplican reglas de filtrado,
NAT, alias, certificados SSL, portal cautivo, autenticación SSH basada
en llaves públicas y un sistema de prevención de intrusiones (Fail2ban),
con el fin de comprender de manera práctica los principios de defensa en
profundidad y segmentación de redes.

\hypertarget{objetivo-general}{%
\subsection{Objetivo general}\label{objetivo-general}}

Poner en marcha el entorno OPNsense como cortafuegos y enrutador,
configurando una red virtual segmentada en zonas WAN, LAN y DMZ,
aplicando reglas de firewall, NAT, servicios web, acceso SSH seguro,
portal cautivo, certificados SSL y medidas básicas de seguridad.

\hypertarget{objetivos-especuxedficos}{%
\subsection{Objetivos específicos}\label{objetivos-especuxedficos}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Instalar y configurar OPNsense como firewall/router en una máquina
  virtual dentro de GNS3, asignando correctamente las interfaces de red
  WAN, LAN y DMZ.
\item
  Diseñar e implementar una topología de red segmentada, asignando
  direccionamiento IP coherente a cada zona y a los equipos finales
  (cliente Linux Mint y servidor Ubuntu/CentOS).
\item
  Configurar reglas de firewall y NAT en OPNsense que permitan el
  tráfico necesario entre zonas (ICMP, HTTP/HTTPS) y bloqueen el acceso
  no autorizado desde la DMZ hacia la LAN.
\item
  Implementar un servidor web (Apache o Nginx) en la DMZ con soporte
  HTTPS mediante un certificado SSL autofirmado, un portal cautivo en la
  LAN y un sistema de prevención de intrusos (Fail2ban) en el servidor.
\item
  Configurar el acceso remoto SSH mediante autenticación por clave
  pública desde el cliente Linux Mint hacia el servidor de la DMZ, y
  validar todo el entorno mediante pruebas de conectividad y de
  seguridad.
\item
  Proponer una mejora de monitoreo en tiempo real mediante
  notificaciones automáticas a Telegram cada vez que se registre un
  acceso SSH al servidor.
\end{enumerate}

\hypertarget{alcance}{%
\subsection{Alcance}\label{alcance}}

El alcance de esta práctica comprende el diseño, la instalación y la
configuración de un entorno de laboratorio completamente virtual,
ejecutado sobre GNS3 con apoyo de máquinas virtuales (QEMU/VMware) o
contenedores. No se trata de un despliegue en producción ni de un
entorno expuesto a Internet real; el adaptador WAN se conecta a una red
NAT/puente proporcionada por el hipervisor, simulando el acceso a
Internet.

El trabajo abarca: la instalación de OPNsense; la creación y
configuración de las interfaces WAN, LAN y DMZ; la instalación de un
servidor web Linux en la DMZ; la configuración de un cliente Linux Mint
en la LAN; la definición de reglas de firewall y de NAT; la generación
de un certificado SSL autofirmado; la implementación de un portal
cautivo; la configuración de Fail2ban; el acceso SSH mediante llave
pública; y la propuesta de un mecanismo de alertas vía Telegram. Quedan
fuera del alcance la configuración de VPN site-to-site, el balanceo de
carga y la alta disponibilidad, por no ser parte de los requerimientos
de esta práctica.

\section{METODOLOGÍA --- CICLO DE APRENDIZAJE EXPERIENCIAL DE
KOLB}\label{metodologuxeda-ciclo-de-aprendizaje-experiencial-de-kolb}}

Para el desarrollo de esta práctica se utilizó el \textbf{ciclo de
aprendizaje experiencial de David Kolb}, el cual propone que el
conocimiento se construye a través de cuatro etapas cíclicas y
complementarias: la \emph{experiencia concreta} (realizar la actividad),
la \emph{observación reflexiva} (analizar lo sucedido), la
\emph{conceptualización abstracta} (relacionar lo observado con la
teoría) y la \emph{experimentación activa} (aplicar lo aprendido en
nuevas situaciones o proponer mejoras). A continuación, se describe cómo
se aplicó cada etapa dentro del desarrollo de la PAE 5.

\hypertarget{experiencia-concreta-quuxe9-se-hizo}{%
\subsection{Experiencia concreta --- ¿Qué se
hizo?}\label{experiencia-concreta-quuxe9-se-hizo}}

Durante esta etapa se ejecutaron de manera práctica las siguientes
actividades dentro del entorno virtual de GNS3:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Se descargó la imagen oficial de instalación
  \texttt{OPNsense-*-dvd-amd64.iso} desde el sitio web oficial de
  OPNsense.
\item
  Se creó una máquina virtual con un mínimo de \textbf{2048 MB de RAM} y
  \textbf{tres adaptadores de red} (tipo Intel PRO/1000 o virtio),
  correspondientes a las interfaces WAN, LAN y DMZ.
\item
  Se instaló OPNsense sobre dicha máquina virtual y se asignaron las
  interfaces de red desde el menú de consola: la primera interfaz como
  WAN, la segunda como LAN y la tercera como interfaz opcional (OPT1),
  renombrada posteriormente como DMZ.
\item
  Se configuraron las direcciones IP de cada interfaz: WAN obtiene su
  dirección por DHCP/NAT del hipervisor (o de forma estática, p.~ej.
  192.168.1.2/24), LAN se configuró como 50.50.50.1/24 y DMZ como
  172.17.0.1/24.
\item
  Se desplegó un servidor Ubuntu/CentOS dentro de la red DMZ
  (172.17.0.10/24), sobre el cual se instaló y configuró un servidor web
  Apache o Nginx.
\item
  Se desplegó un cliente Linux Mint dentro de la red LAN
  (50.50.50.100/24), configurado con la puerta de enlace 50.50.50.1 y
  servidor DNS.
\item
  Se crearon alias y reglas de firewall en OPNsense para permitir el
  tráfico ICMP y HTTP/HTTPS desde la LAN hacia la DMZ, permitir la
  salida de la LAN hacia la WAN, y bloquear explícitamente el acceso
  desde la DMZ hacia la LAN.
\item
  Se configuró el NAT de salida (Outbound NAT) para que tanto la LAN
  como la DMZ puedan salir hacia Internet (WAN) a través de la dirección
  pública/simulada de OPNsense.
\item
  Se generó un certificado SSL autofirmado para habilitar HTTPS en el
  servidor web de la DMZ.
\item
  Se implementó un portal cautivo en la interfaz LAN, configurado con
  autenticación local de usuarios.
\item
  Se instaló y configuró Fail2ban en el servidor de la DMZ para proteger
  el servicio SSH frente a ataques de fuerza bruta.
\item
  Se generó un par de llaves SSH (pública/privada) en el cliente Linux
  Mint y se configuró el acceso sin contraseña hacia el servidor de la
  DMZ.
\item
  Se realizaron pruebas de conectividad (ping), de navegación
  HTTP/HTTPS, de portal cautivo, de bloqueo de Fail2ban y de acceso SSH
  por llave pública.
\item
  Se diseñó una propuesta de mejora para el envío de alertas automáticas
  a Telegram cada vez que un usuario ingresa por SSH al servidor.
\end{enumerate}

\hypertarget{observaciuxf3n-reflexiva-quuxe9-se-observuxf3}{%
\subsection{Observación reflexiva --- ¿Qué se
observó?}\label{observaciuxf3n-reflexiva-quuxe9-se-observuxf3}}

A partir de la ejecución práctica descrita en la sección anterior, se
realizaron las siguientes observaciones:

\begin{itemize}
\tightlist
\item
  \textbf{La segmentación de red funciona correctamente solo si existen
  reglas explícitas.} Por defecto, OPNsense bloquea todo el tráfico
  entrante en las interfaces opcionales (como la DMZ) y no permite
  comunicación entre zonas si no existe una regla que lo autorice. Esto
  comprueba el principio de ``denegación por defecto'' (\emph{default
  deny}).
\item
  \textbf{El NAT de salida permite que los equipos de la LAN y la DMZ
  naveguen hacia Internet} siempre que OPNsense tenga configurada
  correctamente la interfaz WAN y el modo de NAT (automático o híbrido).
  Sin esta configuración, los equipos internos no podrían resolver ni
  alcanzar direcciones públicas.
\item
  \textbf{El tráfico ICMP (ping) está bloqueado por defecto entre
  interfaces.} Para que un equipo de la LAN pueda hacer ping a la DMZ (o
  a la propia interfaz de OPNsense), es indispensable crear una regla
  específica que permita el protocolo ICMP en la interfaz
  correspondiente.
\item
  \textbf{El certificado SSL autofirmado genera una advertencia de
  seguridad en el navegador} (``conexión no privada'' o ``certificado no
  confiable''), debido a que no fue emitido por una autoridad
  certificadora reconocida. Sin embargo, la conexión HTTPS se establece
  correctamente y el tráfico viaja cifrado.
\item
  \textbf{El portal cautivo intercepta todo el tráfico HTTP de la red
  LAN} y redirige al usuario hacia una página de autenticación hasta que
  ingrese credenciales válidas; una vez autenticado, el usuario obtiene
  acceso normal a la red según las reglas de firewall configuradas.
\item
  \textbf{Fail2ban detecta automáticamente los intentos fallidos de
  inicio de sesión SSH} registrados en los archivos de log del sistema,
  y bloquea de forma temporal (mediante reglas de firewall locales) la
  dirección IP del atacante tras superar el número de intentos
  configurado.
\item
  \textbf{La autenticación SSH mediante llave pública elimina la
  necesidad de contraseña} y reduce significativamente el riesgo de
  ataques de fuerza bruta, ya que el atacante necesitaría poseer la
  llave privada correspondiente.
\item
  \textbf{GNS3 permite interconectar virtualmente OPNsense, el servidor
  de la DMZ y el cliente Linux Mint sin necesidad de hardware físico
  adicional}, lo cual facilita la repetición de pruebas, la creación de
  instantáneas (\emph{snapshots}) y la corrección de errores de
  configuración sin riesgo para equipos reales.
\end{itemize}

\hypertarget{experimentaciuxf3n-activa-quuxe9-se-puede-mejorar-o-probar-despuuxe9s}{%
\subsection{Experimentación activa --- ¿Qué se puede mejorar o probar
después?}\label{experimentaciuxf3n-activa-quuxe9-se-puede-mejorar-o-probar-despuuxe9s}}

Como propuesta de extensión de la práctica, se plantea la implementación
de un \textbf{sistema de alertas automáticas mediante Telegram}, que
notifique en tiempo real cada vez que un usuario ingresa por SSH al
servidor de la DMZ, indicando el usuario, la IP de origen, el puerto
utilizado y la fecha/hora del evento. Esta mejora permite pasar de un
modelo de seguridad reactivo (revisar logs después de un incidente) a un
modelo de \textbf{monitoreo proactivo}, en el cual el administrador
recibe información inmediata sobre accesos al servidor, lo que facilita
la detección temprana de actividad sospechosa.

Adicionalmente, como líneas futuras de experimentación derivadas de esta
práctica se proponen:

\begin{itemize}
\tightlist
\item
  Integrar un sistema de detección/prevención de intrusos (IDS/IPS) como
  \textbf{Suricata}, disponible como plugin de OPNsense, para
  inspeccionar el tráfico que atraviesa el firewall.
\item
  Configurar \textbf{VLANs} adicionales para separar, por ejemplo,
  dispositivos IoT o de invitados dentro de la misma LAN física.
\item
  Implementar una \textbf{VPN} (OpenVPN o WireGuard) en OPNsense para
  permitir el acceso remoto seguro a la red interna desde el exterior.
\item
  Sustituir el certificado autofirmado por uno emitido por una
  \textbf{autoridad certificadora interna} creada en OPNsense (System
  \textgreater{} Trust \textgreater{} Authorities), de modo que los
  equipos de la LAN confíen automáticamente en los certificados de los
  servidores de la DMZ.
\item
  Centralizar los registros (logs) de OPNsense, del servidor web y de
  Fail2ban en un servidor de monitoreo (por ejemplo, mediante Syslog o
  un stack ELK/Grafana-Loki).
\end{itemize}

\hypertarget{explicaciuxf3n-de-la-topologuxeda}{%
\subsection{Explicación de la
topología}\label{explicaciuxf3n-de-la-topologuxeda}}

La topología implementada está compuesta por un equipo \textbf{OPNsense}
que actúa como enrutador y cortafuegos central, interconectando tres
zonas de seguridad claramente diferenciadas:

\begin{itemize}
\tightlist
\item
  \textbf{Zona WAN (Wide Area Network):} representa la conexión hacia
  ``Internet''. En el entorno virtual, esta interfaz se conecta a la red
  NAT/puente que ofrece el hipervisor (GNS3/VMware), por lo que puede
  recibir una dirección IP por DHCP o configurarse de forma estática
  (por ejemplo, 192.168.1.2/24). A través de esta interfaz, OPNsense
  centraliza la salida hacia el exterior de toda la red interna.
\item
  \textbf{Zona LAN (Local Area Network):} corresponde a la red interna
  de usuarios. Aquí se ubica el cliente \textbf{Linux Mint}
  (50.50.50.100/24), que representa una estación de trabajo de un
  usuario final. La interfaz LAN de OPNsense (50.50.50.1/24) actúa como
  puerta de enlace predeterminada de esta red.
\item
  \textbf{Zona DMZ (Demilitarized Zone / Zona Desmilitarizada):} es una
  subred intermedia, aislada tanto de la LAN como de la WAN, en la cual
  se ubican los servicios que deben ser accesibles desde la red interna
  (y opcionalmente desde el exterior), pero que, por seguridad, no deben
  tener visibilidad directa hacia la LAN. En esta zona se encuentra el
  \textbf{servidor Ubuntu/CentOS} (172.17.0.10/24) con el servicio web
  Apache o Nginx. La interfaz DMZ de OPNsense (172.17.0.1/24) actúa como
  puerta de enlace de esta subred.
\end{itemize}

OPNsense centraliza el control de todo el tráfico que circula entre
estas tres zonas. Por defecto, el tráfico entre interfaces está
\textbf{bloqueado} (política \emph{default deny}), por lo que es
necesario crear reglas explícitas de firewall para permitir únicamente
las comunicaciones requeridas (por ejemplo, ICMP y HTTP/HTTPS desde la
LAN hacia la DMZ), manteniendo bloqueado cualquier intento de la DMZ de
iniciar conexiones hacia la LAN. La siguiente figura resume gráficamente
esta topología:

\hypertarget{descarga-e-instalaciuxf3n}{%
\subsubsection{Descarga e instalación}\label{descarga-e-instalaciuxf3n}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Se descargó la imagen \texttt{OPNsense-*-dvd-amd64.iso} desde el sitio
  oficial \url{https://opnsense.org/download/}, seleccionando
  arquitectura \textbf{amd64} y tipo de imagen \textbf{DVD}.
\item
  En GNS3 (o VMware/VirtualBox), se creó una nueva máquina virtual
  denominada \textbf{OPNsense} con las siguientes características
  mínimas:

  \begin{itemize}
  \tightlist
  \item
    \textbf{Memoria RAM:} 2048 MB (se recomienda 3072--4096 MB para un
    funcionamiento más fluido del panel web).
  \item
    \textbf{Disco duro:} 8--16 GB (suficiente para el sistema base y los
    registros).
  \item
    \textbf{Adaptadores de red:} 3 interfaces virtuales (tipo
    \emph{Intel PRO/1000} o \emph{virtio-net}), que se conectarán
    respectivamente a la red WAN, a la red LAN y a la red DMZ dentro del
    proyecto de GNS3.
  \end{itemize}
\item
  Se montó el archivo ISO descargado como unidad de arranque y se inició
  la máquina virtual.
\item
  Durante el instalador, se seleccionó el teclado (US por defecto), se
  eligió la opción \textbf{Install (UFS)} y se indicó el disco virtual
  de destino.
\item
  Se estableció la contraseña del usuario \texttt{root}, que será
  utilizada tanto para el acceso por consola como para el acceso inicial
  al panel web.
\item
  Al finalizar la instalación, se retiró la imagen ISO y se reinició la
  máquina virtual para arrancar desde el disco.
\end{enumerate}

\hypertarget{reglas-de-firewall-en-opnsense}{%
\subsection{Reglas de firewall en
OPNsense}\label{reglas-de-firewall-en-opnsense}}

OPNsense procesa las reglas de firewall \textbf{de arriba hacia abajo,
aplicando la primera regla que coincida} con el tráfico (similar a
pfSense). Si ningún tráfico coincide con una regla ``Pass'' explícita,
se aplica la política por defecto: \textbf{bloquear todo (default
deny)}. Por ello, fue necesario crear reglas explícitas para permitir el
tráfico legítimo entre zonas y dejar implícito (o reforzar de manera
explícita) el bloqueo del tráfico no autorizado desde la DMZ hacia la
LAN.

\hypertarget{configuraciuxf3n-de-nat}{%
\subsection{Configuración de NAT}\label{configuraciuxf3n-de-nat}}

OPNsense ofrece varios modos de NAT de salida
(\texttt{Firewall\ \textgreater{}\ NAT\ \textgreater{}\ Outbound}):

\begin{itemize}
\tightlist
\item
  \textbf{Automatic outbound NAT:} genera automáticamente reglas de NAT
  para todas las redes internas (LAN, DMZ, etc.) que tengan una ruta
  hacia la interfaz WAN.
\item
  \textbf{Hybrid outbound NAT (recomendado para esta práctica):} permite
  que OPNsense genere las reglas automáticas y, además, el administrador
  agregue reglas manuales adicionales si lo requiere.
\item
  \textbf{Manual outbound NAT:} todas las reglas deben crearse
  manualmente.
\item
  \textbf{Disabled:} desactiva el NAT de salida (no recomendado si se
  desea acceso a Internet).
\end{itemize}

\hypertarget{procedimiento-aplicado}{%
\subsubsection{Procedimiento aplicado}\label{procedimiento-aplicado}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Se accedió a
  \texttt{Firewall\ \textgreater{}\ NAT\ \textgreater{}\ Outbound}.
\item
  Se seleccionó el modo \textbf{Hybrid outbound NAT rule generation} y
  se guardó el cambio.
\item
  OPNsense generó automáticamente las reglas de NAT para las redes
  \texttt{50.50.50.0/24} (LAN) y \texttt{172.17.0.0/24} (DMZ) hacia la
  interfaz WAN, traduciendo (enmascarando) las direcciones internas a la
  dirección IP de la interfaz WAN (192.168.1.2 o la IP asignada por
  DHCP).
\item
  Se verificó que cada regla de NAT tuviera como \textbf{interfaz}
  ``WAN'', como \textbf{origen} la red interna correspondiente y como
  \textbf{traducción/Address} la opción ``Interface address'' (NAT tipo
  \emph{masquerade}).
\end{enumerate}

\begin{Verbatim}[fontsize=\footnotesize,frame=single,rulecolor=\color{codebg},fillcolor=\color{codebg},framesep=2mm,xleftmargin=1mm,xrightmargin=1mm,breaklines=true,breakanywhere=true,breaksymbolleft={},breaksymbolright={}]

# Ping hacia el servidor web de la DMZ

\end{Verbatim}

\textbf{Resultados esperados:}

\begin{itemize}
\tightlist
\item
  La prueba 1 debe responder siempre, ya que corresponde a la puerta de
  enlace directa del cliente.
\item
  Las pruebas 2 y 3 solo responderán correctamente \textbf{si existe la
  regla ``Pass ICMP'' en la interfaz LAN} (sección 3.7.2, regla 1). Si
  dicha regla no existe o está deshabilitada, el ping mostrará tiempo de
  espera agotado (\emph{Request timeout}) y, al revisar
  \texttt{Firewall\ \textgreater{}\ Log\ Files\ \textgreater{}\ Live\ View},
  se observará el paquete ICMP bloqueado.
\item
  Esta prueba demuestra de forma práctica que \textbf{el enrutamiento
  entre subredes existe a nivel IP}, pero el \textbf{firewall es quien
  decide si el tráfico se permite o no}.
\end{itemize}

Como mejora opcional, OPNsense permite crear una \textbf{Autoridad
Certificadora (CA) interna} en

y posteriormente emitir certificados firmados por dicha CA en

confiable'' desaparecerán al navegar por HTTPS hacia los servicios de la
DMZ.

\hypertarget{portal-cautivo-en-la-lan}{%
\subsection{Portal cautivo en la LAN}\label{portal-cautivo-en-la-lan}}

El portal cautivo obliga a los usuarios de la red LAN a autenticarse
mediante una página web antes de poder acceder a Internet o a otros
recursos de la red.

\hypertarget{configuraciuxf3n-paso-a-paso}{%
\subsubsection{Configuración paso a
paso}\label{configuraciuxf3n-paso-a-paso}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Ir a \texttt{Services\ \textgreater{}\ Captive\ Portal}.
\item
  En la pestaña \textbf{Administration}, hacer clic en \textbf{+ Add}
  para crear una nueva zona, por ejemplo \texttt{portal\_lan}.
\item
  Marcar la casilla \textbf{Enable}.
\item
  En \textbf{Interfaces}, seleccionar \textbf{LAN} (la red donde se
  aplicará el portal).
\item
  Configurar los tiempos de sesión:

  \begin{itemize}
  \tightlist
  \item
    \textbf{Idle timeout:} tiempo (en minutos) tras el cual se
    desconecta a un usuario inactivo (p.~ej., 30 minutos).
  \item
    \textbf{Hard timeout:} tiempo máximo de sesión continua (p.~ej., 240
    minutos).
  \end{itemize}
\item
  En \textbf{Authentication}, seleccionar el método \textbf{Local
  Database} (autenticación contra usuarios locales de OPNsense).
\item
  Crear los usuarios que podrán autenticarse en el portal desde
  \texttt{System\ \textgreater{}\ Access\ \textgreater{}\ Users\ \textgreater{}\ Add}
  (por ejemplo, usuario \texttt{estudiante1}, con una contraseña
  segura).
\item
  (Opcional) En la pestaña \textbf{Templates}, personalizar la página
  HTML de inicio de sesión con el logotipo y los colores institucionales
  de la UTA.
\item
  Guardar y aplicar los cambios (\textbf{Save} -\textgreater{}
  \textbf{Apply}).
\end{enumerate}

\hypertarget{comportamiento-esperado}{%
\subsubsection{Comportamiento esperado}\label{comportamiento-esperado}}

Al conectar el cliente Linux Mint a la red LAN y abrir un navegador,
cualquier solicitud HTTP será \textbf{interceptada y redirigida}
automáticamente hacia la página de autenticación del portal cautivo
(típicamente en \texttt{https://50.50.50.1:8003} o similar). Una vez
ingresadas las credenciales válidas, el portal autoriza la dirección
MAC/IP del cliente durante el tiempo configurado, permitiendo el acceso
normal según las reglas de firewall ya definidas.

\hypertarget{configuraciuxf3n-de-fail2ban-en-el-servidor-de-la-dmz}{%
\subsection{Configuración de Fail2ban en el servidor de la
DMZ}\label{configuraciuxf3n-de-fail2ban-en-el-servidor-de-la-dmz}}

Fail2ban es un sistema de prevención de intrusiones a nivel de host que
analiza los archivos de registro (logs) en busca de patrones de fallos
de autenticación repetidos y, al superar un umbral, bloquea
temporalmente la dirección IP del origen mediante reglas de firewall
locales (iptables/nftables).

\begin{Verbatim}[fontsize=\footnotesize,frame=single,rulecolor=\color{codebg},fillcolor=\color{codebg},framesep=2mm,xleftmargin=1mm,xrightmargin=1mm,breaklines=true,breakanywhere=true,breaksymbolleft={},breaksymbolright={}]

Dentro de \texttt{jail.local}, en la sección \texttt{{[}sshd{]}}:

\begin{Verbatim}[fontsize=\footnotesize,frame=single,rulecolor=\color{codebg},fillcolor=\color{codebg},framesep=2mm,xleftmargin=1mm,xrightmargin=1mm,breaklines=true,breakanywhere=true,breaksymbolleft={},breaksymbolright={}]

port     = ssh
filter   = sshd
logpath  = /var/log/auth.log

\begin{itemize}
\tightlist
\item

  permitidos.
\item

\item

\end{itemize}

#!/bin/bash
# Script de alerta de acceso SSH vía Telegram

TOKEN="TU_TOKEN_DEL_BOT"
CHAT_ID="TU_CHAT_ID"

if [ "$PAM_TYPE" = "open_session" ]; then
  HOST=$(hostname)
  FECHA=$(date '+%Y-%m-%d %H:%M:%S')
  MENSAJE="[ALERTA] Acceso SSH detectado%0AServidor: ${HOST}%0AUsuario: ${PAM_USER}%0AOrigen: ${PAM_RHOST}%0AFecha: ${FECHA}"

  curl -s -X POST "https://api.telegram.org/bot${TOKEN}/sendMessage" \
    -d chat_id="${CHAT_ID}" \
    -d text="${MENSAJE}"
fi
\end{Verbatim}

\hypertarget{conclusiones}{%
\section{CONCLUSIONES}\label{conclusiones}}

La implementación de OPNsense como firewall y enrutador permitió comprobar de manera práctica la importancia de segmentar una red en zonas WAN, LAN y DMZ. Esta separación facilita el control del tráfico entre áreas con distintos niveles de confianza y reduce la exposición de los servidores ubicados en la DMZ, ya que cada comunicación depende de reglas explícitas de firewall. Además, la configuración de NAT de salida evidenció cómo los equipos internos pueden acceder a redes externas mediante la traducción de direcciones, manteniendo oculto el direccionamiento privado de la infraestructura.

En general, la práctica demostró que la seguridad de una red no depende de una sola configuración, sino de la integración de varias capas de protección. El uso de HTTPS con certificado SSL, portal cautivo, Fail2ban y autenticación SSH por llave pública fortaleció el entorno frente a accesos no autorizados y ataques de fuerza bruta. Asimismo, el trabajo con GNS3 y máquinas virtuales permitió construir, probar y corregir la topología sin afectar equipos físicos, mientras que la propuesta de alertas por Telegram mostró la utilidad de incorporar mecanismos de monitoreo proactivo para notificar eventos importantes como los accesos remotos por SSH.

  \textbf{Cambiar las credenciales por defecto} del usuario
  \texttt{root} de OPNsense inmediatamente después de la instalación, y
  crear usuarios administrativos individuales con contraseñas robustas
  y, de ser posible, autenticación de dos factores (2FA) para el acceso
  al panel web.
\item
  \textbf{Respaldar periódicamente la configuración de OPNsense} desde
  \texttt{System\ \textgreater{}\ Configuration\ \textgreater{}\ Backups},
  exportando el archivo \texttt{config.xml}, de manera que ante
  cualquier error de configuración sea posible restaurar un estado
  funcional conocido.
\item
  \textbf{Aplicar el principio de mínimo privilegio} al definir las
  reglas de firewall: en lugar de reglas genéricas ``permitir todo'',
  especificar siempre el protocolo, el puerto y las direcciones de
  origen/destino estrictamente necesarios, como se realizó con los alias
  \texttt{RED\_LAN}, \texttt{RED\_DMZ} y \texttt{SRV\_WEB\_DMZ}.
\item
  \textbf{Revisar periódicamente los registros (logs)} de OPNsense
  (\texttt{Firewall\ \textgreater{}\ Log\ Files}), de Fail2ban
  (\texttt{/var/log/fail2ban.log}) y del servidor web
  (\texttt{/var/log/apache2/access.log} y \texttt{error.log}), para
  identificar patrones de tráfico anómalo o intentos de ataque de manera
  oportuna.
\item
  \textbf{Sustituir el certificado SSL autofirmado por uno emitido por
  una autoridad certificadora interna} (creada en
  \texttt{System\ \textgreater{}\ Trust\ \textgreater{}\ Authorities} de
  OPNsense) o, en un entorno de producción real, por un certificado
  emitido por una entidad certificadora pública reconocida (por ejemplo,
  mediante Let's Encrypt), con el fin de evitar las advertencias de
  seguridad en el navegador.
\item
  \textbf{Mantener actualizado el sistema operativo de OPNsense y del
  servidor de la DMZ}
  (\texttt{System\ \textgreater{}\ Firmware\ \textgreater{}\ Updates} en
  OPNsense; \texttt{sudo\ apt\ update\ \&\&\ sudo\ apt\ upgrade} en
  Ubuntu), ya que las actualizaciones suelen incluir parches de
  seguridad críticos para el firewall, Fail2ban, OpenSSH y el servidor
  web.
\item
  \textbf{Extender la segmentación mediante VLANs} para entornos con más
  dispositivos (por ejemplo, separar impresoras, dispositivos IoT o
  redes de invitados), y considerar la incorporación de un sistema
  IDS/IPS como Suricata (disponible como plugin de OPNsense) para
  inspeccionar el contenido del tráfico permitido.
\item
  \textbf{Documentar y versionar las reglas de firewall y NAT} (por
  ejemplo, exportando capturas o archivos de configuración después de
  cada cambio relevante), de modo que cualquier integrante del equipo
  pueda comprender y auditar el estado de la red en cualquier momento.
\end{enumerate}

\section{ANEXO --- LISTA FINAL DE PASOS PRÁCTICOS RESUMIDOS (GUÍA RÁPIDA
DE
EJECUCIÓN)}\label{anexo-lista-final-de-pasos-pruxe1cticos-resumidos-guuxeda-ruxe1pida-de-ejecuciuxf3n}}

Esta lista resume, en orden, todas las acciones que se deben ejecutar en
GNS3/VM para completar la PAE 5 sin perder el hilo del procedimiento. Se
recomienda marcar cada paso conforme se va completando.

\textbf{A. Preparación del entorno}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Descargar la imagen \texttt{OPNsense-*-dvd-amd64.iso} desde
  \texttt{https://opnsense.org/download/}.
\item
  Descargar/preparar las imágenes de Ubuntu (o CentOS) Server y de Linux
  Mint.
\item
  En GNS3, crear un nuevo proyecto y agregar tres nodos:
  \textbf{OPNsense}, \textbf{Servidor DMZ (Ubuntu/CentOS)} y
  \textbf{Cliente LAN (Linux Mint)}, además de dos switches (uno para
  LAN y otro para DMZ).
\end{enumerate}

\textbf{B. Instalación y configuración base de OPNsense}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{3}
\tightlist
\item
  Crear la VM de OPNsense con 2048 MB RAM (mínimo) y 3 adaptadores de
  red.
\item
  Instalar OPNsense (idioma del teclado, instalación UFS, contraseña de
  \texttt{root}).
\item
  Asignar interfaces: WAN (adaptador 1), LAN (adaptador 2), OPT1/DMZ
  (adaptador 3).
\item
  Configurar IPs por consola: LAN = 50.50.50.1/24, DMZ (OPT1) =
  172.17.0.1/24; WAN en DHCP o estática 192.168.1.2/24.
\item
  Acceder al panel web desde el cliente LAN: \texttt{https://50.50.50.1}
  (usuario \texttt{root}).
\item
  Completar el asistente inicial (hostname, dominio, DNS, zona horaria,
  contraseña).
\end{enumerate}

\textbf{C. Configuración de interfaces en el panel web}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{9}
\tightlist
\item
  Revisar/ajustar \texttt{Interfaces\ \textgreater{}\ WAN} (DHCP o
  estática 192.168.1.2/24, desmarcar ``Block private networks'' si
  aplica).
\item
  Revisar/ajustar \texttt{Interfaces\ \textgreater{}\ LAN}
  (50.50.50.1/24) y habilitar DHCP (rango 50.50.50.100--50.50.50.200) si
  se desea.
\item
  Renombrar y habilitar \texttt{Interfaces\ \textgreater{}\ OPT1} como
  \textbf{DMZ} (172.17.0.1/24).
\end{enumerate}

\textbf{D. Configuración de los equipos finales}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{12}
\tightlist
\item
  Configurar IP estática en el cliente Linux Mint: 50.50.50.100/24,
  gateway 50.50.50.1, DNS 8.8.8.8 (vía \texttt{nmcli} o Network
  Manager).
\item
  Configurar IP estática en el servidor DMZ: 172.17.0.10/24, gateway
  172.17.0.1 (Netplan en Ubuntu o \texttt{nmcli} en CentOS).
\item
  Instalar Apache o Nginx en el servidor DMZ y verificar con
  \texttt{systemctl\ status} y \texttt{curl\ http://localhost}.
\end{enumerate}

\textbf{E. Reglas de firewall, alias y NAT}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{15}
\tightlist
\item
  Crear los alias \texttt{RED\_LAN} (50.50.50.0/24), \texttt{RED\_DMZ}
  (172.17.0.0/24), \texttt{SRV\_WEB\_DMZ} (172.17.0.10) y
  \texttt{PUERTOS\_WEB} (80, 443) en
  \texttt{Firewall\ \textgreater{}\ Aliases}.
\item
  Crear en \texttt{Firewall\ \textgreater{}\ Rules\ \textgreater{}\ LAN}
  las reglas: permitir ICMP LAN-\textgreater DMZ, permitir TCP 80/443
  LAN-\textgreater{}\texttt{SRV\_WEB\_DMZ}, permitir
  LAN-\textgreater cualquier destino (salida a Internet).
\item
  Crear en \texttt{Firewall\ \textgreater{}\ Rules\ \textgreater{}\ DMZ}
  la regla de bloqueo DMZ-\textgreater LAN (en la parte superior) y las
  reglas de salida DMZ-\textgreater WAN (DNS, HTTP, HTTPS).
\item
  Configurar
  \texttt{Firewall\ \textgreater{}\ NAT\ \textgreater{}\ Outbound} en
  modo \textbf{Hybrid} y verificar que se generen las reglas de NAT para
  LAN y DMZ hacia WAN.
\end{enumerate}

\textbf{F. Pruebas de conectividad}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{19}
\tightlist
\item
  Desde Linux Mint: \texttt{ping\ -c\ 4\ 50.50.50.1},
  \texttt{ping\ -c\ 4\ 172.17.0.1}, \texttt{ping\ -c\ 4\ 172.17.0.10}.
\item
  Desde Linux Mint: \texttt{curl\ http://172.17.0.10} y
  \texttt{curl\ -k\ https://172.17.0.10}; abrir ambas URLs en el
  navegador.
\item
  Verificar la salida a Internet: \texttt{ping\ -c\ 4\ 8.8.8.8} o
  \texttt{curl\ https://www.google.com} desde la LAN y la DMZ.
\end{enumerate}

\textbf{G. Seguridad adicional}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{22}
\tightlist
\item
  Generar el certificado SSL autofirmado con
  \texttt{openssl\ req\ -x509\ ...} y configurarlo en Apache/Nginx;
  reiniciar el servicio.
\item
  Configurar el portal cautivo en
  \texttt{Services\ \textgreater{}\ Captive\ Portal} para la interfaz
  LAN, con autenticación local.
\item
  Instalar y configurar Fail2ban (\texttt{jail.local}, sección
  \texttt{{[}sshd{]}}) en el servidor DMZ; verificar con
  \texttt{fail2ban-client\ status\ sshd}.
\item
  Generar llaves SSH en Linux Mint (\texttt{ssh-keygen\ -t\ ed25519}),
  copiar la clave pública con \texttt{ssh-copy-id} y verificar acceso
  sin contraseña.
\item
  (Opcional) Endurecer SSH (\texttt{PasswordAuthentication\ no},
  \texttt{PermitRootLogin\ no}) solo después de confirmar el acceso por
  llave.
\end{enumerate}

\textbf{H. Mejora propuesta y cierre}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{27}
\tightlist
\item
  Crear un bot de Telegram con BotFather, obtener el token y el
  \texttt{chat\_id}.
\item
  Crear el script \texttt{/usr/local/bin/ssh-alert.sh}, integrarlo en
  \texttt{/etc/pam.d/sshd} y probar con un inicio de sesión SSH.
\item
  Tomar todas las capturas de la tabla de evidencias (sección 3.17)
  durante cada paso correspondiente.
\item
  Revisar que todas las pruebas (ping, HTTP/HTTPS, portal cautivo,
  Fail2ban, SSH y Telegram) funcionen correctamente y guardar/respaldar
  la configuración final de OPNsense.
\end{enumerate}
